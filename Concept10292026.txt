The background is:

I should add - my RAG systems are not high performance. They might be - let this 100 page human resources (HR) manual be the golden truth. Let users ask questions from the HR manual.  Or a similar application from IT help desk

In the C#/.NET ecosystem - we are very slow to bring new software products and especially new vendors into our production applications. 

A new vendor's products = another huge chance at security vulnerabilities

And there  is a high hurdle to even consider a new vendor:
- product has to be actively maintained
- we have to prove we have a correct license
- has to be covered by snyk and sonarqube security
etc.  

So the challenge of this exercise is:

Is there a good reason to look past SQL Server for a third party Vector Database?

And SQL Server 2025 added the Vector data type

<<SQL Server 2025 introduces a native VECTOR data type designed to store vector embeddings directly alongside traditional relational data. This feature eliminates the need for external vector databases, making SQL Server fully capable of supporting AI-powered semantic search, machine learning, and Retrieval-Augmented Generation (RAG) applications.>>

Plus there are a lot of people out there saying C# is slow, .NET is slow, SQL Server is slow, Entity Framework is slow.

So let's test that and see

We basically tested three different databases:

1. SQL Server Enterprise Developer 2025
2. SQL Server Express 2025 (it is free)
3. In memory cached data. Mostly just C# code loading the embeddings into memory and then searching memory data store

In the introduction of this article, I want to include the following, to give the reader - how much of a document are we talking about?

For our synthetic corpus, roughly:
Chunks	Approximate Word pages
1,000	150–200 pages
10,000	1,800–2,400 pages


These estimates assume single-spaced text at approximately 500 words per page. Double spacing would roughly double the page count.

Our original passages contain about 75–100 words each. The additional 9,000 passages include extra deployment details, so they are slightly longer.

Chunk count does not translate to a fixed number of pages. Real documents may use larger chunks and overlapping text; overlap means some words appear in multiple chunks. Our benchmark instead treats each short synthetic passage as one chunk.

We ran tests with 1000 chunks and separate tests with 10000 chunks

We also simulated some loading. We would simulate 1 person doing searches, 4, 8 and 16 people doing searches

We created 10 different questions to search the database

My feeling is - we tested / simulated enough to show that SQL Server 2025 is good for 80% of RAG applications.

We included SQL Server Express 2025 - because 1. it is free 2. everything in Express should be copy-paste into SQL Server standard (and higher) versions - when you need higher performance

A developer can do initial prototyping and testing using (free) SQL Server Express 2025. Once they have it proven - upgrade to SQL Server 2025

Our analysis showed that SQL Server Enterprise developer uses 8 parallel threads(or is it workers?) for execution

Whereas SQL Server Express uses only 1. Everything in Express is sequential

That is the purpose of this exercise. For probably 80% of your RAG applications - SQL Server 2025 is probably a good choice
